# Use `workspace_shared_paths` as the repo-policy name, and make the setup atomic from the operato

## Outcome

Use `workspace_shared_paths` as the repo-policy name, and make the setup atomic from the operator’s point of view.

The important design shift is: validate shared-path setup before `jj workspace add` creates anything. If a required shared path cannot be created, `jx work add` should fail with no workspace registered and no directory to repair. Rollback remains a safety net for unexpected post-create failures, not the normal repair path.

```toml
[repo]
workspace_shared_paths = [".pi"]

[[repo.rules]]
repo = "example-owner/example-repo"
workspace_shared_paths = [".pi", ".foo/bar/baz"]
```

All entries are required in the first version. Optional shared paths can be a future richer shape if needed.

## Phase Details

### Phase 1: Repo-policy shared path surface

Add `workspace_shared_paths` to base repo policy and matching repo rules.

The effective list composes in declaration order and deduplicates normalized repo-relative paths. Validation rejects empty paths, absolute paths, `..`, and paths that escape the repo-relative namespace.

### Phase 2: Work-add planning from the primary checkout

`jx work add` should build an explicit plan before mutating anything:

- repository identity,
- primary checkout root,
- destination workspace root,
- selected target revision,
- task metadata intent,
- effective `workspace_shared_paths`.

The primary checkout is always the source of truth, even when `jx work add` runs inside an existing managed workspace.

### Phase 3: Shared-path preflight before workspace creation

Preflight should reject deterministic failures before `jj workspace add`:

- source path missing in the primary checkout,
- destination workspace path already exists,
- shared path would collide with content from the target revision,
- nested shared path needs a parent that would be a checked-out file,
- duplicate or overlapping configured paths create ambiguous results.

This is the repairability boundary: normal config/filesystem errors leave nothing behind, so the operator can fix and rerun.

### Phase 4: Conservative symlink application boundary

After successful preflight and workspace creation, apply symlinks in one filesystem boundary:

- create destination parent directories,
- symlink `workspace/path -> primary/path`,
- fail on unexpected existing destination.

If an unexpected post-create failure happens, `jx` should best-effort forget and remove the workspace, then report the original setup error plus cleanup failure if rollback also fails.

### Phase 5: Success commit point and shell cd

`jx work add` should only report success and emit hidden shell cd output after:

### Phase 6: preflight passes,

### Phase 7: jj workspace creation succeeds,

### Phase 8: metadata is written when needed,

### Phase 9: shared paths are linked.

Shell integration should only `pushd` after that full setup point, so it never lands the operator in a workspace missing required local config.

### Phase 10: Docs and tests

Document `workspace_shared_paths` under repo policy. Tests should cover policy composition, path validation, `.pi` directory sharing, nested parent creation, preflight failures, rollback fallback, and shell cd output only after complete setup.

## Working Log

### 2026-05-13 — Planning turn
Request:
  explain these three checkes:

   - shared path would collide with content from the target revision,
   - nested shared path needs a parent that would be a checked-out file,
   - duplicate or overlapping configured paths create ambiguous results
Response:
  These checks are about avoiding a workspace that is created successfully but cannot be prepared with the required shared paths.

  1. `shared path would collide with content from the target revision`

  `jj workspace add` checks out a revision into the new workspace. If that revision already contains the configured shared path, we cannot also place a symlink there.

  Example:

  ```toml
  workspace_shared_paths = [".pi"]
  ```

  But the target revision has a tracked `.pi` file or directory. After checkout, `workspace/.pi` already exists, so `workspace/.pi -> primary/.pi` cannot be created safely.

  Preflight should catch this before creating the workspace.

  2. `nested shared path needs a parent that would be a checked-out file`

  For a nested shared path, `jx` may need to create parent directories in the workspace.

  Example:

  ```toml
  workspace_shared_paths = [".foo/bar/baz"]
  ```

  To symlink `baz`, `jx` needs:

  ```text
  workspace/.foo/bar/
  ```

  If the target revision has `.foo` as a file, or `.foo/bar` as a file, then `jx` cannot create the parent directory structure. That is different from the final symlink path colliding; the blocker is one of the parents.

  So these should fail preflight:

  ```text
  target revision contains .foo          # file
  target revision contains .foo/bar      # file
  ```

  3. `duplicate or overlapping configured paths create ambiguous results`

  Exact duplicates are easy: normalize and dedupe.

  ```toml
  workspace_shared_paths = [".pi", "./.pi"]
  ```

  Both mean `.pi`, so keep one.

  Overlaps are more dangerous:

  ```toml
  workspace_shared_paths = [".pi", ".pi/settings.toml"]
  ```

  If `.pi` is symlinked as a directory, then `.pi/settings.toml` is already inside that symlinked tree. Creating another symlink inside it is either impossible, redundant, or points into the primary checkout in a surprising way.

  Another example:

  ```toml
  workspace_shared_paths = [".foo", ".foo/bar/baz"]
  ```

  If `workspace/.foo` becomes a symlink, then `workspace/.foo/bar/baz` is no longer a normal workspace path to create.

  I’d treat prefix overlaps as invalid for the first version. Exact duplicates dedupe; parent/child overlaps fail with a clear config error. That keeps behavior easy to reason about.
